# Record Fragment v2: additive schema

The Record Fragment base tables were already present in the shared v1/v2 Supabase project `htbiyakelekprnuxucjc`. On 2026-09-20, `observation-audio-v2.sql` was applied there through the Supabase SQL Editor. A follow-up query confirmed all three audio columns, the owner update policy, and the private `record-audio` bucket. `record-fragments-v2.sql` includes the same voice additions for a fresh installation; do not run both files on a fresh installation. These scripts do not backfill legacy content or change existing `play_sessions`, `generated_texts`, `photo_records`, or `play-photos`.

`record_fragments` owns one original record. Audio/photo/video/artifact source files use private Storage paths in subtype tables; transcription and AI interpretations are separate, append-only results. Teacher revisions are separate and never updated by AI regeneration. `record_fragment_children` and play/story link tables represent many-to-many relationships. The API-facing `RecordFragment` type is a composed view, not one database row.

No existing audio can be backfilled: the current home recorder keeps it in browser memory. For existing `generated_texts`, backfill only a verified original `source_text` or version-1 `input.observation` as a `text` fragment, with the legacy ID as a unique retry key. Never copy generated `result_text` into `raw_text`; do not infer photo subtype from filenames. Preserve legacy rows and file paths. `photo_records.photo_group_id` exists but has no foreign-key constraint, and no public table with `photo_group` in its name appeared in the schema listing; do not treat it as an established group relation. Run a dry-run count by user and legacy ID, insert in batches, then compare counts, source text, ownership, and photo paths before enabling new reads. Existing legacy deletion/expiry behavior must be reconciled before dual-write or UI cutover.

The current project does not establish canonical class/child tables. `class_id` and child IDs remain nullable/unconstrained UUIDs until those tables and ownership rules are confirmed. No endpoint or UI has been switched to this schema. Planned API: `/api/record-fragments` list/create, `/api/record-fragments/[id]` read/update, plus separate source upload, transcription result, interpretation, and teacher-confirmation endpoints. All must authenticate and enforce ownership, consent, private Storage access, and retry-safe writes.
